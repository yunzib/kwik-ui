# 依赖管理

## 结构
- `third_party/`：9 个三方库全部**快照内嵌**（普通文件随主仓 git 分发），零 submodule
- 每库版本/许可/提取规则/补丁登记于 `third_party/README.md`（权威载体）
- 引入入口唯一：`cmake/modules/Dependencies.cmake`（FFmpeg 构建驱动在 `FFmpeg.cmake`，由其 include）
- 我方补丁：主仓普通提交（烤入快照）+ `patches/<lib>/0001-*.patch`（升级重放材料）

## 协作者构建（零网络、零 submodule）
    git clone <仓库>
    cmake -B build -G Ninja
    cmake --build build -j
- FFmpeg 视频后端额外需要本机 Git bash + mingw32-make（工具依赖，非网络）；
  缺失时自动降级 Null 播放器，不影响其余功能
- 裁剪开关：`KWIK_ENABLE_VIDEO=OFF`（不编视频）、`KWIK_ENABLE_G3D=OFF`（不编 3D）、
  `KWIK_ENABLE_CHART=OFF`（不编图表）

## 升级三方库（维护者 SOP）
1. `scripts/vendor_update.ps1 -Lib <库名> -Ref <tag>`
2. 补丁冲突 → 人工合并 → 更新 `patches/<lib>/*.patch`
3. 更新 `third_party/README.md` 的 Version 行
4. 验证门禁：零警告 build + ctest + smoke 38/38（FFmpeg 升级后删 build/ffmpeg-build 重 configure）
5. 单次 commit：`vendor: <lib> <版本> + 补丁`

对比原理：升级 diff = 同一提取规则下的旧快照 commit ↔ 新快照 commit，
只含"我们关心的文件"；`.github/`/`tests/`/`doc/` 从未入库，故永不参与 diff，
其内容属上游自有资产（上游 CI/测试套件），构建不消费，无需同步。

## 打补丁纪律
1. 直接改主仓快照文件 → 单独 commit「patch: <原因>」
2. 同步一份 `.patch` 到 `patches/<lib>/`（升级时重放）
3. 能上游化的尽量提 PR，长期持有补丁越少升级越省

## 新增三方依赖流程
1. `vendor_update.ps1` 规则表 + README 登记该库
2. `Dependencies.cmake` 引入（守卫清单同步加名字）
3. 门禁验证 + CHANGELOG
